# macOS 菜单栏按键行为摘要设计

日期：2026-08-03

状态：对话设计已批准，等待书面规格复核

## 背景

Kivo 当前在 macOS 菜单栏创建一个原生 Tray Icon。菜单只展示聚合设备状态、打开主窗口和退出应用，不能直接看出每台可用设备的按键配置。

本次改动在原生菜单中增加只读的按键行为摘要。用户无需打开主窗口即可确认设备当前 Runtime Assignment 实际会执行的行为。

## 目标

- 在 macOS 原生菜单栏中展示每台可用设备的全部按键。
- 为每个按键展示首个行为摘要；后续行为显示为 `+N`。
- 通过原生子菜单的 hover 交互展示全部行为步骤。
- 多设备时按设备分组；只有一台可用设备时移除设备分组层级。
- 设备或配置变化后自动刷新，同时避免无变化的周期性菜单重建。
- 保持菜单只读，不从菜单栏触发粘贴、快捷键或其他按键行为。

## 非目标

- 使用自定义 WebView 弹层代替 macOS 原生菜单。
- 从菜单栏执行、编辑或重排按键行为。
- 修改现有 Runtime Assignment、按键执行协议或配置持久化格式。
- 为其他操作系统增加相同菜单能力。
- 在原生菜单中完整展示任意长度的粘贴文本。

## 可用设备

行为菜单只包含同时满足以下条件的设备：

1. 设备在线。
2. 设备处于 Runtime 模式。
3. 设备身份有效。
4. Runtime Assignment 有效。
5. Assignment 引用的 Device Profile 和 Hardware Profile 均可解析。

设备临时处于 `configuring`、`learning` 或 `runtime_error` 时仍保留其行为列表。这些状态不改变其 Assignment，也不应导致菜单层级反复消失。无效 Assignment 不展示行为，继续由现有设备状态汇总提示需要处理。

## 菜单结构

菜单顶部保留不可点击的聚合设备状态。底部保留“打开 Kivo”和“退出 Kivo”。行为区域位于状态汇总与应用命令之间。

### 无可用设备

显示一个不可点击的“暂无可用设备”菜单项。

### 一台可用设备

直接在主菜单平铺该设备的全部按键，不显示设备标题或设备子菜单：

```text
2 online · 1 ready · 0 bootloader · 0 errors
---------------------------------------------
确认 · “订单号 123…” +2  ›
复制 · ⌘C               ›
取消 · 未配置
---------------------------------------------
Open Kivo
Quit Kivo
```

### 多台可用设备

主菜单为每台设备展示一个设备子菜单。悬停设备名后进入该设备的按键列表。同一 Device Profile 分配给多台设备时仍分别展示，不能按配置去重：

```text
前台键盘  ›
后台键盘  ›
```

设备顺序沿用 Device Status 的稳定顺序。按键顺序严格沿用 Device Profile 中 group 和 button 的声明顺序，不按名称或是否配置行为重新排序。

### 文案语言

菜单静态文案跟随 `Workspace.settings.language`，与当前配置的 `zh-CN` / `en-US` 设置一致。设备名称、Device Profile 名称和按键名称属于用户数据，不做翻译。

中文使用“等待设备”“暂无可用设备”“未配置”“打开 Kivo”“退出 Kivo”等文案；英文使用现有的 `Waiting for device`、`Not configured`、`Open Kivo` 和 `Quit Kivo`。聚合状态中的 online、ready、bootloader 和 errors 同样按 Workspace 语言格式化，避免同一菜单混用中英文。

## 行为摘要

主菜单按键标题格式为：

```text
<按键名称> · <首个行为摘要> +<剩余行为数>
```

只有一个行为时不显示 `+0`。没有行为时显示 `<按键名称> · 未配置`，并将菜单项设为不可用。

### 粘贴文本

- 主摘要折叠首尾空白、连续空白和换行，然后显示前 12 个字符。
- 文本被截断时追加省略号。
- 摘要使用引号区分文本与按键名称，例如 `确认 · “订单号 123…”`。
- hover 子菜单中的单个粘贴行为最多显示 80 个字符。
- 原始换行在完整摘要中显示为 `↵`，不会把一个原生菜单项拆成多行。
- 超过 80 个字符时仍追加省略号，避免原生菜单宽度超出屏幕。

“hover 展示全部”指展示该按键的全部行为步骤，不表示无限长度展示粘贴正文。

### 快捷键

快捷键使用 macOS 常见缩写：

| 配置键 | 摘要 |
| --- | --- |
| `cmd` | `⌘` |
| `alt` / `option` | `⌥` |
| `ctrl` | `⌃` |
| `shift` | `⇧` |
| `enter` | `↩` |
| `tab` | `⇥` |
| `backspace` | `⌫` |
| `escape` | `Esc` |
| `delete` | `Del` |
| `space` | `Space` |
| `up` / `down` / `left` / `right` | `↑` / `↓` / `←` / `→` |
| `home` / `end` | `Home` / `End` |
| `page_up` / `page_down` | `PgUp` / `PgDn` |

字母按键使用大写，数字保持原样。组合键不插入分隔符，例如 `cmd + shift + k` 显示为 `⌘⇧K`。

### hover 子菜单

每个已配置按键都使用原生子菜单，包括只有一个行为的按键。悬停后按实际执行顺序展示全部步骤：

```text
1. “订单号：123456”
2. ⇥
3. “密码：example”
```

子菜单内容只读。菜单事件仍只接受现有的打开主窗口和退出应用命令；设备、按键和行为条目不会执行 Runtime 行为。

## 菜单模型

在 `tray` 模块中引入可比较的纯 Rust 菜单模型，分离数据投影与 Tauri 原生对象构建：

```text
TrayMenuModel
├── status_label
└── devices[]
    ├── device_id
    ├── device_name
    └── buttons[]
        ├── button_id
        ├── button_label
        ├── primary_summary
        └── action_summaries[]
```

投影函数接收当前 `DeviceStatus` 列表和只读 `Workspace`，解析每台设备的 Runtime Assignment，再按 Device Profile 布局生成按键项。模型不持有 Tauri 句柄，因此摘要、过滤、排序和层级选择可以通过普通 Rust 单元测试验证。

原生菜单构建函数根据模型选择零设备、单设备或多设备结构，创建 `Menu`、`Submenu`、不可点击的 `MenuItem` 和分隔线，然后一次性调用 `TrayIcon::set_menu` 替换菜单。

## 刷新流程

后台设备扫描仍是统一刷新入口：

1. 扫描器取得最新 Device Status。
2. 在 Workspace 读锁内生成新的 `TrayMenuModel`。
3. 新模型与上一次成功安装的模型比较。
4. 模型相同则不操作原生菜单。
5. 模型变化则切换到主线程，构建并替换完整菜单。
6. 替换成功后记录新模型并更新 Tray Icon tooltip。

Workspace 的配置保存、设备改名、Assignment 变更、导入、删除或恢复会在下一轮设备扫描时进入模型。当前扫描间隔约为 500ms，因此菜单最多延迟一个扫描周期刷新。

不采用按菜单项句柄增量更新。布局编辑、设备上下线以及单设备和多设备层级切换都会改变菜单结构，完整替换更容易保证没有陈旧条目。

## 文本安全

所有来自配置的菜单文本在创建原生菜单项前统一处理：

- 主摘要先将所有空白（包括换行）折叠为单个空格，再移除剩余不可见控制字符。
- hover 摘要先将 `CRLF`、`CR` 和 `LF` 统一替换为可见的 `↵`，再折叠其他空白并移除剩余不可见控制字符。
- 将原生菜单用于 mnemonic 的 `&` 转义为 `&&`。
- 截断按 Unicode 字符迭代，不按 UTF-8 字节切割中文或其他 Unicode 文本。

Device ID 和 Button ID 仅用于模型身份与测试断言，不作为可执行菜单命令。只有固定 ID `open-main` 和 `quit-app` 会进入事件路由。

## 错误处理

- Workspace 读锁暂时不可用时跳过本轮刷新，保留上一份有效菜单。
- Assignment 无法解析时跳过该设备的行为区域，不猜测或回退到 Editor Profile。
- 原生菜单构建或替换失败时保留上一份有效菜单，不影响设备扫描、粘贴协调器或按键 Runtime。
- 摘要遇到空动作列表时按“未配置”处理；配置验证仍负责阻止无效粘贴文本和快捷键进入 Workspace。
- 初始化阶段尚未发现设备时正常展示等待状态和“暂无可用设备”。

## 测试与验收

### 单元测试

在 `tray` 模块覆盖：

- 零、一、多个可用设备的层级选择。
- 在线状态、Runtime 模式、身份和 Assignment 的过滤边界。
- 同一 Device Profile 分配给多台设备时保持独立设备分组。
- Device Profile 的 group/button 顺序保持不变。
- 未配置按键、单行为和多行为 `+N`。
- 所有快捷键缩写。
- `zh-CN` 和 `en-US` 的静态菜单文案。
- 中文、英文和其他 Unicode 粘贴文本的字符边界截断。
- 连续空白、换行、控制字符和 `&` 的清理。
- 相同模型不会触发原生菜单重建的变化判定。
- 菜单事件只路由 `open-main` 和 `quit-app`。

### 自动验证

- 运行 `rtk cargo test --manifest-path src-tauri/Cargo.toml tray`。
- 运行完整 Rust 后端测试。
- 运行 Tauri/前端生产构建，确认菜单改动没有破坏打包。
- 运行 `rtk git diff --check`。

### macOS 原生验收

启动原生应用后检查：

1. 单台可用设备直接显示按键，无设备分组 UI。
2. 多台可用设备分别进入各自子菜单。
3. 所有按键可见，未配置项不可用。
4. 首行为和 `+N` 正确。
5. hover 能展开全部行为步骤。
6. 长文本不会把菜单撑出屏幕。
7. 菜单保持打开时，无内容变化的后台扫描不会打断 hover。

若验收时没有可用实体设备，自动化结果不能替代上述原生菜单交互检查；最终报告必须将其标记为未运行。

## 验收标准

- macOS 菜单栏能反映每台可用设备当前 Runtime Assignment 的真实按键配置。
- 一台可用设备时没有冗余设备分组；多台时按设备隔离。
- 每个按键显示首行为摘要和正确的剩余数量。
- hover 子菜单展示全部行为步骤，且粘贴文本长度受控。
- 无配置按键保留并明确显示“未配置”。
- 菜单不会执行设备行为，也不会因无变化的周期扫描被重复替换。
- 任何菜单刷新失败都不会影响现有设备 Runtime。
